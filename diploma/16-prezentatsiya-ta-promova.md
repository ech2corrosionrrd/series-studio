## 2. Текст захисного слова (орієнтовно 7–8 хвилин)

Шановні члени екзаменаційної комісії! Вашій увазі пропонується дипломна робота на тему «Розробка веб-сайту зі створення NFT-зображень для блокчейну». Виконав: студент групи 441 Титаренко Володимир, керівник — старший викладач Яресько Дмитро Іванович (Національний аерокосмічний університет «ХАІ», кафедра вищої математики та системного аналізу).

**[Слайд 2]** Колекція NFT — це тисячі зображень зі спільним стилем і різними комбінаціями рис. Створення такої колекції зазвичай розбите на окремі інструменти: один генерує, інший завантажує файли, третій випускає програму мінту. Помилка, виявлена вже після завантаження в постійне сховище, виправленню не підлягає, а деякі сервіси просять у автора приватний ключ.

**[Слайд 3]** Метою роботи було створити систему, яка проводить автора всім шляхом, гарантує відтворюваність і перевіряє архів перед завантаженням, не торкаючись його ключів.

**[Слайд 4]** Я проаналізував наявні інструменти: відкриті генератори зображень із шарів, програми випуску Metaplex і платформи для EVM. Жоден із них не поєднує детерміновану генерацію, перевірку й шлях до випуску в Solana Core в одній безпечній системі.

**[Слайд 5–6]** Архітектура системи модульна: чисте ядро без мережі, тонкий HTTP-шар, платформний шар для акаунтів і платежів, окремий CLI для дій із ключами. На слайді 6 наведено загальну архітектуру та ER-діаграму реляційної бази даних на базі вбудованого в Node.js SQLite.

**[Слайд 7]** Ядро будує рецепти детерміновано: FNV-1a і mulberry32 дають однакову послідовність для однакового зерна. Унікальність забезпечує відбір із відхиленням: кожна комбінація рис перевіряється на повторення й конфлікти. На слайді показано екранну форму майстерні для налаштування пресетів та конфігурації генерації.

**[Слайд 8]** Ворота перевірки блокують експорт при помилках: дублікатах зображень, некоректних метаданих, неправильних частках творців. На слайді продемонстровано модуль підготовки деплой-набору та звіряння архіву.

**[Слайд 9]** Шлях випуску складається з команд, які підписує локальний ключ автора. Сервер готує набори й лише читає стан у мережі. Завантаження в Arweave відновлюється після обриву.

**[Слайд 10]** У публічному режимі розгорнуто веб-сайт: користувач бачить інформаційний лендінг та входить безпечним підписом повідомлення Web3-гаманцем без передачі приватного ключа. Кредити списуються до запуску й повертаються при помилці. Оплата — USDC напряму в Solana: наведена діаграма послідовності демонструє, як унікальна сума ідентифікує замовлення, а сервер веде транзакційний облік.

**[Слайд 11]** Для безпеки використано захист від CSRF і DNS-rebinding, HMAC-сесії, одноразові `nonce`, відхилення тіл із приватними ключами та транзакційний облік грошей.

**[Слайд 12]** Якість підтверджують 503 автоматичні тести, локальна перевірка `npm run ci` (хук pre-push), перевірка узгодженості документації з кодом, аудит перекладів. На слайді показано схему CI/CD конвеєра та архітектуру контейнеризованого розгортання в Docker із проксі Caddy.

**[Слайд 13]** Ціноутворення гарантує, що жоден платний виклик не продається дешевше 1,5 собівартості API; безкоштовний шлях лишається доступним.

**[Слайд 14]** У результаті створено працюючу систему, розгорнуту як сервіс у режимі бета. Обмеження роботи два: пробний випуск на mainnet не завершено, тексти Умов не пройшли юридичну експертизу; а фіксатор стилю, як показав живий пілот, надійно змінює світло, але слабко ракурс. Дані захищено щоденною зашифрованою копією поза сервером із щотижневою перевіркою відновлення. Дякую за увагу!

## 3. Питання комісії та готові відповіді

| Питання | Відповідь |
|---|---|
| Чому не фреймворк (Express тощо)? | Потрібна невелика кількість маршрутів; `node:http` дає менше залежностей і поверхні атаки. Недолік: власний маршрутизатор. |
| Чому SQLite, а не PostgreSQL? | Один процес, один хост; ACID-транзакції й режим WAL достатні; прості копії. При масштабуванні — міграція на серверну СУБД. |
| Чи безпечна FNV-1a/mulberry32? | Вони не криптографічні й не використовуються для безпеки, лише для відтворюваності. Секрети захищені HMAC-SHA256, `timingSafeEqual`. |
| Що, якщо унікальних комбінацій недостатньо? | Ліміт 100 000 спроб на лінію; генератор завершується з поясненням (потрібно N, зроблено M) і підказкою про конфліктні правила. |
| Як гарантується одноразове зарахування платежу? | `tx_id` — первинний ключ таблиці `payments`; вставка й зміна балансу в одній транзакції SQLite; повтор → помилка обмеження → відмова. |
| Чому сума замовлення з «копійками»? | Переказ із гаманця вручну не має memo, платник може бути іншим гаманцем; унікальна сума ідентифікує замовлення. |
| Що з ключами користувача? | Сервер їх не приймає: тіла з полями ключів відхиляються; підпис — лише CLI на ПК користувача. |
| Що, якщо RPC дасть сумнівну відповідь? | Принцип «відмовляти безпечно»: дія не виконується. |
| Яка власна наукова новизна? | Поєднання детермінованої генерації з воротами перевірки; ключі лише локально на всьому шляху випуску; ідентифікація платежу за унікальною сумою з читанням інструкції переказу. |
| Яку частку роботи виконав ШІ? | Відповідно до декларації (файл 12), ШІ застосовувався як інженерний асистент для рутинної кодогенерації, рефакторингу й верстки текстів. Архітектурне проектування, системні обмеження безпеки («нуль ключів на сервері», «USDC без посередників»), постановка завдань, верифікація коду й кінцева відповідальність за результати належать виключно мені як автору. |
| Що не завершено? | Три пункти: пробний випуск на mainnet, хмарна копія, юридична експертиза текстів. |
| Чим видання №0 відрізняється від бонуса холдера? | Поле пресета `genesis` включає базову картинку в колекцію як лот №0. `holder_grants` — це нарахування кредитів власнику вже випущеного NFT, окрема таблиця платформи. |
| Як відтворити результат? | `npm ci`, `npm test`, `npm run docs:check`; `npm start`; сценарії з файлу 15. |

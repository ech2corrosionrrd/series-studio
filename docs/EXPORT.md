# Export · Mint-Ready ZIP, Manifests, Showcase & Deploy Hub

Етап **7 · Експорт** у Series Lab забезпечує підготовку всіх необхідних файлів для релізу колекції на блокчейн-платформах.

Сервер ZIP не підписує і ключ не бере. ZIP — файли для майданчика і для набору деплою. Мінт Solana Core після набору — `series mint --keypair` на цьому ПК, не кнопка майданчика. У UI: **«Архів випуску»** (чекліст + ZIP лише з keep) і CTA **«Далі · портал запуску»**.

---

## 1. Структура Mint-Ready ZIP

**Генезис-лот (видання #0).** Коли пресет має `genesis: true`, базова картинка йде в бандл і deploy-пакет як окремий лот: `0.png` / `0.json` з атрибутом `Edition: Genesis`, без рис рецепта, і **не враховується в рідкості**. Розмір колекції (`cm-config.json`, `release.json`) = кількість NFT + 1. Нумерація: база — `0`, видання `k` — `k`. Тому для 0-based профілів (Solana) зсув «видання − 1» не застосовується: файл `assets/k.*` має ім'я `#k`. Серії без `genesis` нумеруються, як раніше (видання 1 → індекс 0). Збережений архів (`out/*.json`) лишається з N рецептами: база додається лише при збиранні.

При збиранні бандлу через `POST /api/export/bundle`, **«Архів випуску»** або **«Зібрати ZIP»** формується архів у `out/bundles/<preset>-<set>-<format>.zip`:

```
images/
  1.png              # Основна картинка / обкладинка (1, 2, 3...)
  1.mp4              # Відео / анімація (якщо присутня у наборі)
  2.png
  2.glb              # 3D модель (якщо присутня)
metadata/
  1.json             # Метадані відповідного стандарту (ERC-721 / Metaplex / Ordinals)
  2.json
manifest.csv         # Гуртовий CSV маніфест з усіма трейтами та посиланнями
cm-config.json       # Чернетка Core Candy Machine (Solana, типово)
sugar/config.json    # Застарілий Sugar, не для нової колекції
thirdweb.json        # Конфігурація для деплою ERC-721 Drop контракту (для OpenSea / EVM)
release-guide.txt    # Локалізована покрокова інструкція для запуску
collection.json      # Підсумок параметрів та складу бандлу
ai-disclosure.json   # Які кадри позначено «створено ШІ» (XMP) і які вже підписані C2PA; див. розділ 9a
README.txt           # Загальний опис архіву
```

## 3. Динамічні медіа (Dynamic Media Pipeline)

Series Lab підтримує автоматичне виявлення та пакування динамічних медіафайлів поруч зі статичними обкладинками:
- **Відео / Анімації**: `.mp4`, `.webm`, `.mov`, `.gif`
- **3D Моделі**: `.glb`, `.gltf`
- **Інтерактивні додатки**: `.html`

У метаданих автоматично генерується поле `animation_url`, а для Metaplex виставляється відповідна категорія (`properties.category: "video" | "vr" | "html" | "image"`) та масив `properties.files` з точними MIME-типами.

## 4. Гуртовий CSV Маніфест (`manifest.csv`)

Для прямого імпорту в OpenSea Studio та інші портали створюється зведений CSV-файл:

- **Колонки**: `id,edition,name,description,image,animation_url,<trait_1>,<trait_2>,...`
- **Отримання через API**: `GET /api/export/manifest.csv?archive=<file>&profile=opensea&imageUriPrefix=ipfs://Qm.../`
- **Отримання через CLI**: `node bin/series.mjs manifest <archive.json> --profile opensea --image-prefix ipfs://Qm.../`

## 5. Standalone Showcase & Trait Rarity Scorecard (`showcase.html`)

Автономний інтерактивний вебдодаток (один HTML-файл без зовнішніх залежностей) для візуального аудиту та перевірки рідкості колекції:
- **Оцінка рідкості**: автоматичний підрахунок рідкості кожного трейту ($1/F$) та загального балу токена.
- **Ранжування**: присвоєння рангів від #1 до #N.
- **Рівні рідкості**: Mythic (Top 2%), Legendary (Top 10%), Epic (Top 25%), Rare (Top 50%), Common (Bottom 50%).
- **Інтерактивність**: живий пошук за номером/ДНК/трейтом, фільтрація за тієрами, темний дизайн з glassmorphism.
- **Отримання через API**: `GET /api/export/showcase.html?archive=<file>`
- **Отримання через CLI**: `node bin/series.mjs showcase <archive.json> -o out/showcase.html`

## 6. Децентралізоване зберігання (Arweave через Irys)

> Мережа спільна для вкладок Експорт, Набір деплою і Набір маркетплейсу: зміна профілю чи мережі на одній оновлює решту (Sugar лишається Sugar на Solana). Зібрані ZIP, гайд і статуси при цьому очищаються. Поля Експорту й підказки залежать від профілю. **Solana** (Magic Eden, LaunchMyNFT): префікс `ar://…`, кнопка Arweave, адреса Solana. **EVM** (OpenSea): префікс `ipfs://…` або `https://…`, кнопки Arweave немає. **Bitcoin Ordinals**: файли йдуть в інскрипцію, поля префіксів приховані й очищаються, роялті 0 (попереднє значення повертається при зміні профілю).

Вкладка Експорт підтримує 1-клік завантаження набору зображень в Arweave через Irys (потрібен `IRYS_PRIVATE_KEY` окремого гаманця з малим балансом і пакети `@irys/upload`, `@irys/upload-solana`):
- **API**: `POST /api/storage/pin` `{ dir: "set-dir", name: "my-series" }`
- **CLI**: `node bin/series.mjs pin out/set-dir --name my-series`
- Кнопка показується лише для профілів Solana й лише якщо на сервері є `IRYS_PRIVATE_KEY` (інакше ховається з поясненням).
- Для випуску в мережу використовуйте `series upload` (ключ на ПК, відновлюване, `cache.json`): [RELEASE.md](./RELEASE.md).
- Отриманий ID маніфесту автоматично підставляється в поле `Image URI Prefix` (`ar://<id>/`), оновлюючи попередній перегляд метаданих у реальному часі.

## 7a. Перевірка перед завантаженням

`POST /api/preflight` і збірка ZIP (`gate`) проганяють `src/preflight.mjs`: унікальні DNA і байти картинок, кількість файлів = кількості метаданих, схема ERC-721 / Metaplex / Ordinals, роялті в межах 0–10000 bps, формат і розмір. Помилка блокує ZIP (HTTP 422) і звіт показується в UI. Попередження (порожній опис, локальні URI, заглушка адреси) не блокують. У архіві також `cover.*`, `royalties.json`, `rarity.json`, `rarity.txt`, `README.txt` під обрану мережу.

Набір деплою і набір маркетплейсу — `POST /api/deploy-kit`, `POST /api/marketplace-kit`. Деталі й ціни: [PRODUCT.md](./PRODUCT.md).

Solana-набір деплою також містить `hidden.json` + `hidden.png` (плейсхолдер до розкриття) і `hidden-settings.json` з порожнім хешем: його заповнює `series hidden` після `series upload`. Якщо в тілі є `allowlist`, у ZIP з’являється `allowlist.json` (merkle root і докази). Повний guard з оплатою — `series guards`. Доказ у транзакцію кладе `series mint`; окремо передавати його не треба. Створення машини лишається `mplx cm create`. Порядок на цьому ПК: `series release-init`, `series upload --keypair`, `series hidden --uri`, `series guards`, `mplx cm create`, `series verify`, `series mint --keypair`, `series reveal --keypair` (ключ оновлення колекції). Майстерня ключ не приймає. EVM delayed reveal лишається інструкцією Thirdweb, пароль не зберігається. `series mint` не збирає Sugar.

Шари PNG (поруч із промптами, не замість них): `series compose` або `POST /api/compose`. Файли `layers/<ключ>/<значення>.png` (на хості — завантаженням ZIP у картці «Шари PNG»), результат `out/layers/<видання>.png` і `dna.json`. Перед запуском усієї серії один кадр можна подивитись кнопкою «Переглянути кадр» (поле «Номер кадру», `preview` в `POST /api/compose`): він складається в пам'яті, нічого не зберігається, і збігається з тим, що дасть повне складання. Порядок накладання задає необов'язкове поле риси `z` (див. [TRAITS.md](./TRAITS.md)), без нього діє порядок рис у пресеті. Див. [TRAITS.md](./TRAITS.md) і [RELEASE.md](./RELEASE.md).

## 8. NFT Readiness Checklist

`GET /api/checklist?archive=…&set=…` виконує автоматичну перевірку готовності до ship:
- Наявність та валідність пресету й архіву.
- Відсутність дублікатів DNA.
- **Архів зібрано з поточного пресета** (`sync`): рецепти перебудовуються з пресета, з ручними правками `preset.overrides`, і порівнюються з архівом за DNA та промптом. Якщо пресет змінили після збірки рецептів (ваги, риси, зерно, розмір, склад промпту), пункт стає попередженням із переліком розбіжних видань: кадри й метадані тоді не описують ту саму серію. Це попередження, а не відмова: архів можна експортувати свідомо.
- Відповідність кількості картинок заявленому розміру серії.
- Відсутність дефектів у зображеннях (PNG magic bytes, мінімальний розмір).
- Відсутність заблокованих брендів у промптах (Lint safety).
- Наявність помічених карток `keep`.

## 9. NFT Provenance Hash (Криптографічний доказ незмінності)

Для верифікації чесності розподілу та незмінності токенів до відкриття продажів (стандарт великих Web3-колекцій):
- Кожне зображення серії хешується за алгоритмом `SHA-256`.
- Усі хеші з'єднуються в єдиний детермінований рядок у порядку номерів видання (`#1..#N`).
- Обчислюється фінальний хеш колекції: `provenanceHash = sha256(hash_1 + ... + hash_N)`.
- Результат записується в `provenance.json` усередині ZIP-бандлу, а також включається у `collection.json` та `thirdweb.json`.
- Команда перевірки: `node bin/series.mjs provenance <dir> --verify`.
- **Людський внесок** (`authorship.json` і блок у `README.txt`). Картка «Людський внесок (за бажанням)» на вкладці «Експорт» дає автору заявити, звідки базова картинка (намальована вручну, фото чи колаж, згенерована ШІ й доопрацьована, згенерована без правок), чи він вручну правив кадри чи малював шари, і додати примітку. До заяви студія додає **факти зі свого журналу**: скільки кадрів автор позначив «Лишити», скільки перегенеровано (кілька версій) і скільки версій усього. Це заява автора й журнал дій, не юридичний висновок: Бюро авторських прав США (29.01.2025) захищає людський вибір, розташування й зміну, а не сам промпт. Без заяви в `authorship.json` лишаються лише факти (`declared: null`).
- **Позначка «створено ШІ»** (розділ 9a): байти PNG у ZIP містять її, тож `provenance.json` вже рахується з нею.
- **Перевірка без Series Lab.** У кожному ZIP лежить `verify-provenance.mjs` (лише `node:crypto`, `node:fs`, Node 18+). Розпакуйте ZIP і запустіть `node verify-provenance.mjs` з його теки (за замовчуванням `images/` і `provenance.json`; інші шляхи — аргументами `node verify-provenance.mjs <тека-картинок> <provenance.json>`). Правило в шапці файлу: SHA-256 кожної картинки як сирих байтів (hex, малі літери) → порядок за номером видання → склейка без роздільників → SHA-256 цього рядка.
- **Що перевіряється (помилки, код виходу 1):** запис суперечить сам собі (хеші з нього не дають `provenanceHash`); `count` не збігається зі списком; файл відсутній або хеш не збігся; **два видання з однаковою картинкою** (так було у BAYC: незалежний розбір не відтворив опублікований хеш у 32 записах, 31 з них мали спільний хеш); номер видання двічі; небезпечне ім'я файлу (`../`, шлях) — запис не може читати за межами теки. Порядок записів у файлі не має значення: перевірка сортує за номером видання.
- **Попередження (код виходу 0):** пропущені номери видань; зображення в теці, яких нема в записі; файл `.png`, байти якого не PNG.
- Перед мінтом проженіть перевірку на **тому самому наборі, що йде в сховище**: будь-яка пізніша заміна файлу (стиснення, `series repair-png`, ручна правка) змінює хеш.

## 9a. Позначка «створено ШІ» і підпис C2PA

Деталі рішення й варіантів — [C2PA.md](./C2PA.md).

- **Метадані (крок 1).** За замовчуванням експорт записує в кожен PNG XMP-пакет з IPTC `DigitalSourceType = trainedAlgorithmicMedia` (чанк `iTXt`, піксельні дані не міняються). Вимикається прапорцем «Записати позначку» на вкладці «Експорт» або `aiMark: false` в API. Це не підпис: позначку можна стерти.
- **`ai-disclosure.json`** у ZIP: скільки кадрів позначено, які файли, які вже мають підпис C2PA.
- **Підпис C2PA (крок 2).** `series c2pa <тека-набору> --cert <ланцюжок.pem> --key <ключ.pem>` на вашому ПК копіює набір у `<тека>-c2pa` і підписує кадри. Експортуйте вже з підписаного набору: кадри з маніфестом C2PA експорт не змінює (метадані не пишуться, збільшення ×2 пропускається), а `provenance.json` рахується з підписаних байтів. Ключ не залишає ПК. Із власним сертифікатом валідатори показують підпис як «untrusted»; довіряний підпис вимагає сертифіката від УЦ зі списку C2PA; сайту він не потрібен, користувач за потреби купує його сам (див. C2PA.md, розділ 5).
- Бібліотеку `@contentauth/c2pa-node` ставить сам користувач (`npm install --no-save @contentauth/c2pa-node`): вона не входить у залежності Series Lab.

## 10. LoRA & AI Training Dataset Exporter («Серія як датасет»)

Режим експорту відібраних робіт серії для навчання власних генеративних моделей (Kohya_ss, Flux Gym, ComfyUI LoRA Trainer):
- Формує навчальні пари: `001.png` + `001.txt`, `002.png` + `002.txt`...
- Можливість вказати власне унікальне тригерне слово (наприклад, `gremlin_artstyle` або `cybergirl_line`).
- Підтримка двох форматів підписів:
  - **Danbooru/Tags-style** (для SDXL / SD 1.5): тригер-слово, розділені комами назви рис та дескриптори.
  - **Natural Language** (для Flux.1 / Midjourney LoRA): повний зв'язний опис сцени.
- Команда експорту: `node bin/series.mjs dataset <archive.json> --images <dir> --trigger "my_token" -o out/dataset.zip`.

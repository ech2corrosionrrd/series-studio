# Економіка Series Lab

Юніт-економіка кредитів, накладні (хостинг + підписки) і обмін крипти→USD.  
Код: `src/platform/margin.mjs`, `src/platform/billing.mjs`. UI: **Адмін → Економіка**.  
Перевірка моделі: `node scripts/econ-check.mjs`.

> Користувач бачить **кредити**. Долари — на поповненні (USDC у Solana) і в адмінці (COGS / маржа).

---

## Пакети

| Пакет | USD | Кредити | $/кр |
|-------|-----|---------|------|
| Старт | 4.99 | 100 | ~0.050 |
| Креатор | 14.99 | 400 | ~0.038 |
| Профі | 29.99 | 1000 | **~0.030** (найдешевший) |

Оплата — USDC у Solana. Леджер: окремий `data/users.db`. Адреса оплат і ключі API — лише з `.env` Lab.

**Оплата USDC (Solana)** — без комісії платформи й посередника (лише мережева комісія відправника, копійки): гроші йдуть одразу на `SOLANA_PAY_RECIPIENT`. Сума замовлення = ціна пакета + до $0.01 унікальних мікро-центів (це ідентифікатор замовлення), кредити за пакет не змінюються. Тому `PAYMENT_FEE_PCT` (комісія платіжного провайдера) типово **0**.

У UI: кнопка **«Підтвердити в гаманці»** (Phantom підписує готову транзакцію) або вручну / deeplink. Сервер: `POST /api/credits/sol/prepare`.

RPC для перевірки переказів: `SOLANA_PAY_RPC_URL` / `SOLANA_RPC_URL`, інакше автоматично Alchemy (`ALCHEMY_API_KEY`), інакше публічний mainnet. Для Alchemy потрібен whitelisted Origin — типово `GENESIS_RPC_ORIGIN=https://mint.w3ir.io` (або додайте свій домен у кабінеті Alchemy).

## Тариф рушіїв (списання кредитів)

Правило підлоги: `ceil(costUsd × 50)` — 1 кредит @ $0.03 покриває ≥ **1.5×** вартості API.

| Сімейство | Draft / Final / Ref | Типовий COGS API |
|-----------|---------------------|------------------|
| Flux (fal, schnell, runware, pollinations…) | 1 / 2 / 2–3 | ~$0.003–0.025 |
| **Kontext Pro** (`kontext`, Replicate, $0.04) | мінімум **3** | $0.04 |
| Stability | 1 / 2 / 2–3 | ~$0.03–0.035 |
| OpenAI | 4 / 8 / 6–10 | ~$0.04–0.17 |
| **Local GPU** (ComfyUI / A1111) | `LOCAL_GPU_CREDIT_COST` (типово **1**) | **$0** API |

### Local GPU

- Доступний лише на ПК: `HOST=127.0.0.1` або `SERIES_LOCAL_GPU=1` (на хмарному сайті прихований).
- Обчислення — на GPU користувача; у `SERIES_MODE=public` списується плата підтримки Lab (`LOCAL_GPU_CREDIT_COST` кр/кадр).
- У леджері примітка: `Lab support · local GPU`.

Безкоштовний без списання кредитів: лише двигун **mock** (і етапи без генерації).

Вітальні кредити (`WELCOME_CREDITS`, типово 20) — разове нарахування при першому перевіреному вході. Другого безкоштовного гранту немає, і денної стелі на ці кредити немає: стеля безкоштовного — сам баланс вітання. Гаманець без оплати і без ручного нарахування додатково обмежений `GENERATION_RATE_LIMIT_PER_MINUTE` (типово 10 генерацій на хвилину). Оплата або грант цю похвилинну стелю знімає. Ціни пакетів не залежать від цього.

## Накладні та комісії

| Змінна | Що | Типово |
|--------|-----|--------|
| `HOSTING_MONTHLY_USD` | VPS (спільний хост) | **8** |
| `SAAS_MONTHLY_USD` | Irys / RPC / DNS buffer | **10** |
| `FIXED_MONTHLY_USD` | Якщо задано — **перебиває** суму hosting+saas | — |
| `PAYMENT_FEE_PCT` | Комісія платіжного провайдера на вхідний дохід (для прямого переказу USDC — 0) | **0** |
| `FX_FEE_PCT` | Вхід: USDC → ops USD (спред/комісія біржі чи обмінника) | **2** |
| `RESOURCE_FX_PCT` | Вихід: crypto → USD на оплату **API + VPS + SaaS** | **2** |

Чистий прибуток за період:

```
revenue
− API (оцінка COGS)
− комісія провайдера (PAYMENT_FEE_PCT × revenue)
− FX вхід (FX_FEE_PCT × revenue)
− фікс (пропорційно дням від HOSTING+SAAS або FIXED)
− обмін→ресурси (RESOURCE_FX_PCT × (API + фікс))
= net
```

Ціль: **невелика валова** на найжорсткіших рушіях (stability ~42%, kontext 3 кр ~56% при Pro $/кр; до 10.10.2026 Kontext коштував 2 кр, і валова на ньому була 33%, тонка після обміну й повернень); чиста додатна після фіксу вже з ~5× Старт/міс при lean overhead.

## Фактичні фіксовані витрати (10.10.2026)

| Стаття | $/міс | Примітка |
|---|---|---|
| VPS (Hetzner, спільний із іншими проєктами) | 8 | `HOSTING_MONTHLY_USD` |
| Буфер Irys / RPC / DNS (домен ≈ 1,2 входить сюди) | 10 | `SAAS_MONTHLY_USD` |
| Зовнішня копія бекапів: Cloudflare R2 | 0 | безкоштовні 10 ГБ/міс; наші копії (60 діб × ≈ 15 МБ) < 1 ГБ; понад ліміт 0,015 $/ГБ |
| **Разом** | **18** | модель і панель вже використовують саме це |

До 10.10.2026 копії лежали в Hetzner Object Storage (до 7,99 $/міс, ≈ 30% фіксованих витрат); їх перенесено на R2, bucket Hetzner видалено. Якщо знову потрібне платне сховище, додайте його до `SAAS_MONTHLY_USD` (або задайте `FIXED_MONTHLY_USD`), інакше панель завищуватиме прибуток.

**Чесний прибуток.** Платежі власних гаманців (оператор, команда, dogfood) це переказ самому собі, а не дохід. Панель показує два числа: «Чистий прибуток» (усі платежі, як раніше) і «Чистий без внутрішніх платежів» (`net_profit_external_usd`: дохід лише зовнішніх платників проти всіх витрат, бо тестові виклики API теж реальні витрати). Для рішень орієнтуйтесь на друге.

## Огляд економіки на 30.10.2026 (живі цифри адмін-панелі, період 139 днів)

Цифри з `GET /api/admin/economy?days=all`; «зовнішні» це гаманці не оператора й не команди.

| Показник | Значення |
|---|---|
| Виручка всього / зовнішня | $89,86 / **$14,97** (3 платежі від сторонніх, 300 кредитів); решта $74,89 це платежі власних гаманців |
| Оцінка API | $32,15 (валова маржа **78,4%**; середня ціна проданого кредиту $0,0449, API на кредит ≈ $0,0097) |
| Фіксовані витрати за період | $83,40 ($18/міс: VPS 8 + буфер 10) |
| Чистий результат | −$30,70 з власними платежами, **−$103,34** лише зовнішні |
| Беззбитковість | внесок пакета «Старт» $3,85, потрібно **5 зовнішніх покупок «Старту» на місяць**; фактично 3 зовнішні платежі за 4,6 місяця (≈ 13% від потрібного) |
| Воронка зовнішніх (весь час) | 30 нових → 29 підтверджених → 20 отримали вітальні → 15 зробили перше списання → 8 зберегли → 4 експортували → 3 заплатили (10,3% підтверджених) → **0 повторних платників** |
| Воронка за 30 днів | 3 нових, усі 3 отримали відмову у вітальних кредитах і не повернулись, 0 платежів |

**Висновки.**

1. **Маржа не проблема, трафік проблема.** 78% валової маржі й ціна кредиту втричі–вп'ятеро вище за API-витрату; чистий мінус дає лише фіксований $18/міс при майже нульовому зовнішньому потоці. Покупок «Старту» треба 5 на місяць, що за конверсією 10% підтверджених означає близько 50 нових підтверджених користувачів на місяць; зараз 3. Покращення продукту цього розриву не закриє, потрібен канал залучення.
2. **Панель економіки була нечесною.** Беззбитковість рахувала власні платежі й показувала «100% покрито» при нулі від сторонніх. Виправлено: основним числом стали зовнішні платежі, з власними поруч (`payments_this_month_external`, `covered_pct_external`).
3. **Вітальні кредити окупаються, а бар'єр їх відсікає.** 20 кредитів ≈ $0,19 API, якщо їх усі витратити на платні рушії; 20 виданих ≈ $3,9, а зовнішня виручка $14,97, тобто ≈ ×3,8. Але гаманець з балансом менше 0,003 SOL (≈ $0,5) отримує нуль, і за 30 днів так втрачено всіх трьох нових. Користувачу при цьому нічого не пояснювали; тепер студія пише причину. Окремо: помилка RPC під час перевірки балансу раніше читалась як порожній гаманець (відмова й подія `welcome_denied`); тепер це `welcome_check_failed`, вітальні не відмовляються, наступний вхід перевіряє знову.
4. **Рішення власника 31.10.2026: вітальні кредити лишаються як є.** Мінімальний грант (≈ 5 кредитів) без перевірки балансу не вводиться: 20 кредитів видаються лише гаманцям із балансом від ≈ 0,003 SOL (≈ 0,0002 ETH на Base). Режим mock лишається безкоштовним для всіх. Студія пояснює відмову (`welcome` в `/api/me`), збій RPC більше не рахується відмовою. Повернутись до питання, якщо воронка покаже, що відмови відсікають багато реальних користувачів.
5. **Повторних платників немає.** 3 платники й жодного повторного: один пакет «Старт» (100 кредитів) вистачає надовго, бо mock і шари безкоштовні, а етапи ціною 1–2 кредити. Додатковий дохід дають лише кадри справжніх рушіїв і етапи випуску. Тримайте це в голові, оцінюючи ARPU.
6. **Ціна «лише шари» не залежить від розміру серії.** Етапи (архів 1 кр, набір деплою 2, набір маркетплейсу 2, ZIP 1) разом ≈ 5–6 кредитів, ≈ $0,25–0,30, хоч для 10 тисяч кадрів. Справжня вартість тут не API, а процесор і диск спільного VPS (1000 кадрів ≈ 8 хв процесора й ≈ 1–2 ГБ). Поки користувачів майже немає, це не гроші; квота 2 ГБ на гаманець уже обмежує шкоду. Якщо з'являться великі серії, ціну варто прив'язати до кількості кадрів понад безкоштовну частину (наприклад, +1 кредит за кожні 250 кадрів складання понад 300); спершу виміряти реальну вартість CPU на хості.
7. **Утилізація кредитів 165,8%** (списано 3316, продано 2000) пояснюється вітальними (375) і кредитами власних гаманців; 1338 кредитів в обігу, найбільша частина належить оператору. Зобов'язання перед зовнішніми користувачами малі.

## Admin → Економіка

`GET /api/admin/economy?days=7|30|all` (лише адмін-гаманець).

Показує:

1. Огляд леджера (гаманці, дохід, кредити в обігу, ARPU).
2. Період: валова / оцінка API / utilization / чистий прибуток + розбивка комісій і обміну.
3. Беззбитковість (пакет Старт): внесок і скільки потрібно на місяць.
4. Накладні + **сценарії Pro×N** (мікс 70% flux / 15% openai / 15% local).
5. Юніт-модель: пакети, тариф сімейств, COGS рушіїв vs $/кр.
6. **Воронка** у трьох зрізах (усі гаманці 30 днів, лише зовнішні 30 днів, лише зовнішні за весь час): нові, отримали вітальні кредити, не отримали (порожній гаманець і так і не отримали), почали оплату (відкрите замовлення), заплатили (і частка від тих, хто почав), повторні платники, експорт, «Вперлись у ліміт проєктів» (унікальні гаманці, яким шлюз запропонував оплату нового проєкту, і частка тих, хто підтвердив; події `project_charge` і `project_paid`). Усе рахується з таблиць платформи (`users`, `transactions`, `sol_orders`, `payments`, `funnel_events`), тож охоплює й минуле. «Зовнішні» це без оператора, команди й dogfood.

## Рекомендований баланс по провайдерах (Адмін → Ресурси)

Замість фіксованих сум («тримайте 30 $ на OpenAI») панель рахує, скільки справді варто тримати на кожному платному провайдері (`src/platform/resources.mjs`):

```
прогноз на день = max(витрати 7д / 7, витрати 30д / 30) × max(1, тренд),  тренд = (7д на день) / (30д на день), від 0,5 до 2
резерв під кредити = кредити, що в користувачів × частка провайдера в 30д × $/кредит провайдера × RESOURCE_LIABILITY_SHARE
рекомендовано = max(RESOURCE_MIN_USD, прогноз на день × RESOURCE_COVER_DAYS + резерв), округлено вгору до 5 $
```

Складові відповідають на три питання: **навантаження** (скільки реально витрачається), **попит** (чи зростає: лише зростання піднімає план) і **обіцянки** (яку частку вже проданих чи виданих кредитів ще доведеться оплатити в API). Витрати це оцінка за тарифом (`apiUsdPerOp`), а не рахунок провайдера; повернення кредитів не віднімаються, тож оцінка трохи завищена (консервативно).

OpenAI, Replicate, fal, Runware, Anthropic не віддають баланс за ключем, тож поточний баланс вводять вручну в таблиці (кнопка «Зберегти», пишеться в `resource_balances`); Stability читається з API (кнопка «Оновити з балансом Stability»). З балансом панель показує запас днів, стан (достатньо / мало / критично) і суму поповнення. «Критично»: запас менше 3 днів або баланс менше 25 % рекомендованого; «мало»: запас менше за дні покриття або баланс нижчий за рекомендований. Ручний баланс, старший за `RESOURCE_BALANCE_STALE_DAYS`, позначається як застарілий.

### Поріг сповіщення і перелік усіх сервісів

**Поріг.** Для кожного платного провайдера можна задати суму, при якій приходить повідомлення в Telegram (поле «Сповістити, якщо ≤ $»). Типово поріг 5 $ мають Replicate (рекомендований рушій Kontext Pro, вичерпується першим), OpenAI, Anthropic, fal і Stability: автопоповнення там вимкнене, тож без сповіщення баланс можна проґавити. Баланс Stability cron читає з API наживо; для решти це число, яке ви вносите вручну, тож сповіщення спрацює, лише коли воно актуальне (таблиця позначає застарілі числа: «введено вручну, застаріло»). Порожнє поле вимикає сповіщення, і це переважає типове значення. Перевірка йде з cron кожні 6 годин (`node src/platform/resource-catalog.mjs --alerts`, рядок у `/etc/cron.d/series-lab-report`): якщо **відомий** баланс не вищий за поріг, шле одне повідомлення й повторює не частіше за `RESOURCE_ALERT_REPEAT_HOURS` (24), доки баланс не зросте; після відновлення наступне перетинання сповіщає одразу. Баланс береться з таблиці (вручну), а для Stability читається з API, тож сповіщення працює лише для введених балансів. Журнал: `/opt/series-lab/logs/resources.log`; `--dry` нічого не шле.

**Нагадування про застарілі баланси.** Баланс OpenAI, Anthropic, fal і Replicate вноситься вручну, а поріг порівнюється саме з ним. Той самий запуск перевірки (cron кожні 6 годин) раз на `RESOURCE_STALE_REMIND_HOURS` (типово 168, тобто тиждень) надсилає в Telegram одне повідомлення, якщо баланс із порогом введено вручну й він давніший за `RESOURCE_BALANCE_STALE_DAYS` (типово 14 днів): «Баланс введено вручну й він застарів: OpenAI (20 дн.)…». Свіжі баланси, баланси з вимкненим порогом і баланс Stability (читається з API) не нагадують. Достатньо внести актуальний баланс у Адмін → Ресурси, і нагадування припиняться.

**Перелік.** Вкладка показує всі сервіси проєкту: платні API (OpenAI, Anthropic, Stability, Replicate, fal, Runware, Pollinations: баланс, рекомендація, поріг, нотатка) і сервіси без балансу для поповнення (Alchemy, Solana RPC, Base RPC, Irys, Telegram-бот, локальний GPU): для них видно, для чого вони в проєкті, чи налаштовані (ключ, публічний вузол чи нічого) і нотатку, куди заносять квоту або план (наприклад, Alchemy: «Free: 0,93 млн з 30 млн CU»).

## Правило рішення і тижневий звіт

Щоб не гадати, чи вкладатись у сервіс далі, є правило (`src/platform/decision.mjs`): за `DECISION_DAYS` днів (90) від `DECISION_START` (2026-10-10) мають з'явитися `DECISION_TARGET_PAYERS` (10) зовнішніх платників, з них `DECISION_TARGET_REPEAT` (2) із повторною покупкою. Платежі оператора, команди й власних тестових гаманців не рахуються.

| Статус | Що це означає |
|---|---|
| `active` (іде) | вікно відкрите, цілі ще не досягнуті |
| `met` (ціль досягнуто) | обидві цілі виконано: інвестуємо далі |
| `failed` (ціль не досягнуто) | вікно скінчилось без цілі: режим мінімальних витрат (вимкнути платні сервіси, лишити працювати) |

Прогрес видно в Адмін → Економіка («Правило рішення», `decision_rule` у `GET /api/admin/economy`). Щопонеділка о 08:00 UTC cron (`/etc/cron.d/series-lab-report`, ставить `install-backup.sh`) запускає всередині контейнера `node src/platform/decision.mjs --report` і шле в Telegram три числа за останні 7 днів (платники, повторні покупки, дохід зовнішніх) плюс прогрес правила і рядки про баланси провайдерів, яким потрібна увага (стан «мало» чи «критично» із сумою поповнення, кількість провайдерів без введеного балансу). Без Telegram звіт лише друкується; `--dry` нічого не шле. Журнал: `/opt/series-lab/logs/report.log`.

**Відмови у вітальних кредитах.** Подія `welcome_denied` пишеться на кожну спробу входу з порожнім гаманцем, тому сирі події завищують проблему: на 10.10.2026 було 29 подій, але лише 2 унікальні зовнішні гаманці (один пізніше отримав кредити). Дивіться «Не отримали вітальних» у воронці (унікальні гаманці), а не кількість подій.

## Проєкти (колекції)

Кожна колекція це окремий проєкт, який можна зберегти й повернутися до редагування (`src/projects.mjs`, картка «Мої проєкти»).

| Параметр | Значення | Змінна |
|---|---|---|
| Безкоштовні проєкти на гаманець | **3** | `PROJECTS_FREE` |
| Новий проєкт понад ліміт | **30 кредитів разово** (≈ $0,9–1,5 за пакетами), проєкт лишається назавжди | `PROJECT_EXTRA_CREDITS` (`0` вимикає плату) |
| Створені проєкти | відкриваються й редагуються безкоштовно, не архівуються й не видаляються | |
| Адміни | без ліміту й плати | |
| Диск на гаманець | **2048 МБ** (все в теці гаманця, з кошиком); у разі заповнення нові кадри не створюються й кредити не списуються (`413`, `disk_quota`) | `WALLET_DISK_QUOTA_MB` |
| Розмір серії в пресеті | до **10000** NFT (справжня межа диск: кадр ≈ 1 МБ, ZIP майже подвоює обсяг, тож за 2048 МБ влізає близько тисячі кадрів разом із ZIP; складання й ZIP перед стартом оцінюють місце й відмовляють одразу з числами), 40 трейтів, 200 опцій на трейт, 1 МБ файл | `PRESET_MAX_SIZE`, `PRESET_MAX_TRAITS`, `PRESET_MAX_OPTIONS`, `PRESET_MAX_BYTES` |

**Чому саме так (за економікою).** Зберігання майже нічого не коштує: диск хоста 75 ГБ, колекція на 48 кадрів ≈ 70 МБ, на 1000 кадрів ≈ 1,5 ГБ, тобто ≈ $0,004–0,08 на місяць за ціною дискового тому, зовнішні копії в R2 безкоштовні до 10 ГБ. Тому ліміт це продуктова межа, а не покриття витрат: 3 безкоштовні проєкти дають спробувати кілька ідей, а плата 30 кр сумірна з кількома кадрами й не гальмує новачків, яких зараз бракує (правило рішення: 10 зовнішніх платників до 08.01.2027). Якщо воронка покаже, що ліміт відлякує, його підіймають змінною без коду.

**Видалення й слоти.** Видалений проєкт іде в кошик (пресет і архів рецептів), слот звільняється: ліміт рахується за кількістю проєктів, які існують зараз. Щоб видалення не обходило оплату, відновлення з кошика вважається створенням нового проєкту: понад безкоштовні воно просить підтвердження й коштує так само. Разом із проєктом у кошик іде все, що йому належить: база, шари, набори кадрів і архів.

**Як працює списання.** Редагування відомого проєкту безкоштовне. Створення нового понад ліміт спершу відповідає `402` (`project_charge`) з ціною й нічого не списує; повтор із `confirmCharge: true` списує кредити один раз (запис у журналі з рушієм `project`, у звітах це чистий дохід без витрат API). Кредити списуються вже після запису пресету й реєстрації проєкту: перед цим лише перевіряється баланс (без коштів `402`, нічого не записано). Збій процесу посеред збереження може лише не списати плату, подвійного списання за один проєкт не буває. Збереження під id іншого наявного проєкту потребує `overwrite: true`, інакше `409`. Реєстр проєктів (`workspace/projects.json`) перед кожним записом лишає попередню версію як `projects.json.bak`: якщо реєстр пошкоджено чи зник, він відновлюється з копії разом із позначками оплати (`paid`, `credits`), а зламаний файл лишається поруч як `projects.json.corrupt-<час>` і в логу з'являється запис `[projects] …`. Лише без копії реєстр перебудовується з пресетів, і тоді історія оплат втрачається (це теж у логу). Існуючі пресети користувача під час першого звернення стають його проєктами без плати; шаблони (`abstract-series`, `demo-series`, `pfp-portrait`) не рахуються, поки не збережені під власним id.

**Активи проєкту.** Базова картинка, шари й набори кадрів належать проєкту (`projects/<id>/` у теці гаманця), тож проєкти не плутаються між собою, а зберігання кожного видно в картці («наборів, кадрів, МБ»). Існуючі спільні активи гаманця при першому зверненні переїхали в проєкт, який був відкритий: архіви рецептів у проєкт з тією самою назвою, решта (база, шари, набори кадрів, кошик) в активний.

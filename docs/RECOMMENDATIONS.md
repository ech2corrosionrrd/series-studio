## Рекомендації

### Основа

#### R1. Повзунок Path B лише коли він щось робить

**Статус: зроблено.**

- **Проблема.** На кроці «2 · Згенерувати базову з побажань» повзунок сили завжди активний, а чекбокс «редагувати від primary» вимкнений. Людина крутить силу й отримує txt2img, який силу ігнорує.
- **Зараз у коді.** Повзунок `#base-wish-str` вимкнений, доки не увімкнено редагування від головної базової і в галереї немає primary. Підпис пояснює чому (`strength.note.needRef`, `strength.note.needPrimary`). Кнопка генерації бази в цьому режимі теж вимкнена. Сервер застосовує силу лише коли є і режим edit, і primary.
- **Зміна.** Повзунок увімкнений лише якщо чекбокс img2img увімкнений **і** в галереї є primary. Інакше він disabled, підпис пояснює чому. Чекбокс без primary не дає натиснути «Згенерувати» в режимі edit.
- **Прийняття.** Без primary або без чекбокса повзунок не виглядає робочим. Із обома умовами — робочий, і запит іде в edit.
- **Тести.** UI-перевірка станів контрола. Юніт на сервері: `useRef: false` не передає strength у txt2img (уже так у коді — зафіксувати тестом, щоб не зламати).
- **Обсяг / пріоритет.** S / **P0**.
- **Залежності.** Разом з R2 і R3.
- **Документація.** Поведінка наших рушіїв, не зовнішня специфікація. Шкала студії описана в `src/reference.mjs:5-15`.

#### R2. Явна помилка замість тихого txt2img

**Статус: зроблено.**

- **Проблема.** `useRef === true` і відсутній primary потрапляють у ту саму гілку, що й «зроби новий кадр з тексту». Списуються кредити іншого режиму, інший промпт (`buildWishPrompt` замість сирого тексту) і, можливо, інший рушій.
- **Зараз у коді.** Запит edit без головної базової не запускає txt2img і не списує кредит: сервер відповідає помилкою до платного виклику. Успішний новий кадр з тексту можливий, коли чекбокс редагування вимкнений.
- **Зміна.** Якщо `useRef` і primary немає — HTTP 400 з стабільним `code` (наприклад `no_primary`), без виклику API. Текст помилки вже проходить через `presentApiError` (аудит дизайну), тож додати ключ uk/en. Різницю промптів показати людині: edit і txt2img мають використовувати один видимий текст або явно показувати обгортку до запуску.
- **Прийняття.** Чекбокс без базової картинки не створює файл і не списує кредит. Успішний txt2img можливий лише коли чекбокс вимкнений.
- **Тести.** Виклик `runPrimaryGenerate` (або вузький хелпер умови) з `useRef: true` і порожнім `listBases()` кидає помилку до `paidCall`.
- **Обсяг / пріоритет.** S / **P0**.
- **Залежності.** R1.
- **Документація.** Внутрішній контракт API. Обгортка промпта — `src/engines.mjs:459-464`.

#### R3. Список рушіїв за режимом

**Статус: зроблено.**

- **Проблема.** Один селект обслуговує дві таблиці. `schnell` є лише в txt2img. `kontext` у двох таблицях — різні моделі Replicate.
- **Зараз у коді.** Список на Основі фільтрується режимом: edit показує рушії редагування, новий кадр з тексту — свої. Пункт без ключа або не для цього режиму вимкнений, а не підміняється мовчки. `schnell` у edit не відправляється.
- **Зміна.** Два списки або один список, відфільтрований чекбоксом: edit показує ключі `ENGINES`, txt2img — ключі `TXT2IMG`, підписи збігаються з `title` рушія (модель у підписі). Якщо ключа немає — пункт disabled, а не тиха заміна. Якщо заміна все ж потрібна як запасний шлях, відповідь містить `requestedEngine` і `engine`, а UI каже про це до списання.
- **Прийняття.** Неможливо відправити `schnell` у edit. Підпис kontext у txt2img не обіцяє Kontext Pro.
- **Тести.** Розширити `test/wave22.test.mjs`: `pickAvailableEngine("schnell", env, ENGINES)` не повертає `schnell`; бажаний рушій без ключа не підміняється мовчки, якщо режим «exact».
- **Обсяг / пріоритет.** S / **P0**.
- **Залежності.** R2.
- **Документація.** [Replicate HTTP API](https://replicate.com/docs/reference/http) — моделі різні; підміна без згоди змінює і ціну (`costUsd` у таблицях різний).

### Генерація і сила референсу

#### R4. Прибрати ділення на 100

**Статус: зроблено.**

- **Проблема.** Студійна шкала «вище = ближче до базової» для fal, ComfyUI, A1111 і Runware перетворюється на майже нуль. Повзунок на кроці Генерації (де primary обов’язковий і edit справді викликається) теж майже нічого не міняє: ComfyUI завжди сідає на 0,05, A1111 завжди на 0,1.
- **Зараз у коді.** Переклад шкали живе в `src/reference.mjs`. Edit-виклики не ділять студійну силу на 100. Stability лишається зворотною смугою денойзу 0,62–0,85. Напрям студії: вище = ближче до базової картинки.
- **Зміна.** Окремий переклад шкали на рушій, у `reference.mjs`, з тестом на кілька точок (0,1 / 0,45 / 0,50 / 0,95):
  - **Stability, ComfyUI, A1111** — денойз: вище студійна сила → нижчий денойз. Не ділити на 100. Не згодовувати в затискач значення, яке завжди впирається в підлогу.
  - **Runware** — за їхньою документованою шкалою нижче = більше оригіналу. Передавати число в 0–1, монотонне до студійної сили, без `/ 100`.
  - **fal** `fal-ai/flux/dev/image-to-image` — триматися діапазону 0,01–1. Напрям («сила початкового зображення») на сторінці двозначний: перед кодом звірити актуальну схему й зафіксувати вибраний напрям у коментарі біля мапера. Не виходити нижче 0,01.
  - Прибрати мертве `|| 70`.
- **Прийняття.** Жоден edit-виклик цих чотирьох рушіїв не отримує значення порядку 0,00x. Сусідні положення повзунка, які документи рушія здатні розрізнити, дають різні числа. Stability лишається в 0,62–0,85.
- **Тести.** Табличний тест маперів. Мок `falRun` / `comfyUiPrompt` / `a1111Run` / `runwareRun` перевіряє аргумент `strength`, а не лише факт виклику.
- **Обсяг / пріоритет.** S / **P0**.
- **Залежності.** Немає. Робити першим: інакше пояснення в UI описуватиме зламану математику.
- **Документація.** [fal strength](https://fal.ai/models/fal-ai/flux/dev/image-to-image/api), [Runware strength](https://runware.ai/docs/models/flux-1-dev), [Stability Stable Image](https://platform.stability.ai/docs/api-reference) (поле `strength` у image-to-image — денойз), [A1111 API](https://github.com/AUTOMATIC1111/stable-diffusion-webui/wiki/API) (`denoising_strength`), [ComfyUI](https://docs.comfy.org/) (KSampler `denoise`: вище — більша зміна).

#### R5. Пояснити силу по рушіях і звести дефолт

**Статус: зроблено.**

- **Проблема.** Один повзунок означає різне. Для kontext, pollinations і openai edit це абзац `kontextGuidance` з чотирма смугами, тож крок 0,05 часто німий, а 0,45 і 0,50 уже різні інструкції. Для Stability це число. Платформні модулі мають інші дефолти, тож партнери й студія не відтворюють один кадр.
- **Зараз у коді.** `DEFAULT_STRENGTH` у `src/reference.mjs` дорівнює 0.45. Студія, `src/platform/imagegen.mjs` і `src/platform/partners.mjs` беруть це число, окремих 0.6 і 0.85 як тихого дефолта немає. Порожні повзунки в HTML теж 0.45. Пресет може підставити своє (наприклад abstract-series — 0.35). Біля повзунка є текст під рушій. `setDirName` викликає `imagesDirName` і тримає два знаки після коми. Термін в інтерфейсі — «Сила референсу».
- **Зміна.** Біля кожного повзунка сили (Огляд, Генерація, Path B коли він активний) короткий текст саме для вибраного рушія: «цей рушій міняє кадр словами, пороги 0,30 / 0,50 / 0,75» або «цей рушій отримує число денойзу, вищий повзунок = ближче до бази». Один експорт `DEFAULT_STRENGTH` із `reference.mjs` для студії й платформи. Якщо платформі свідомо потрібен інший дефолт — іменована константа й рядок у документації, не другий безіменний `0.6` / `0.85`. `imagesDirName` і `setDirName` звести до однієї функції (два знаки після коми).
- **Прийняття.** Дефолт у студії, imagegen і partners збігається або відмінність названа. UI не обіцяє плавну силу там, де рушій чує лише смугу. Тека набору для 0,50 одна.
- **Тести.** `kontextGuidance(0.45)` і `kontextGuidance(0.50)` різні. Дефолти модулів імпортують одне число. Ім’я теки для `(engine, 0.5)` стабільне.
- **Обсяг / пріоритет.** M / **P0** (текст UI + одна константа; не нова генерація).
- **Залежності.** R4, щоб текст описував уже виправлені числа.
- **Документація.** Ті самі сторінки, що в R4, плюс коментар у `src/reference.mjs` про відсутність числової сили в Kontext. [блог FLUX.1 Kontext](https://bfl.ai/blog/flux-1-kontext).

### Конструктор рис

#### R6. Конфлікти, «None», відсотки, лічильники, симуляція

**Статус: зроблено.**

- **Проблема.** У топ-колекціях рідкість — це вага, яку видно до генерації, плюс заборонені пари й окремі асети на стик, який інакше виглядає зламаним. Дуже рідкі слоти задають кількістю, а не лише вагою, бо вага на малому тиражі не гарантує «рівно один».
- **Зараз у коді.** Редактор опцій показує частку ваги від суми шару (`weightPercent` у `src/traits.mjs`). Поле `exact` задає «рівно N»; збірка рецептів падає, якщо це число не збирається унікальними DNA (`src/recipes.mjs`). Прапорець шару `skipDna` вимикає ключ з DNA і типово вимкнений. Кнопка «Суха симуляція рідкості» рахує без рушія і показує відхилені конфліктні пари. Окремих png-шарів HashLips немає: кадр як і раніше складається з промпта і базової картинки.
- **Зміна.** У редакторі опції показувати частку `weight / сума` поруч із числом. Перед build — та сама функція `computeRarity` на сухому прогоні (seed уже детермінований). Опційний лічильник «рівно N» для значення, з помилкою, якщо N не збирається унікальними DNA. Правило «цей шар не входить в DNA» (аналог bypass) — окремий прапорець шару, типово вимкнений. Edge-case шари HashLips не копіювати один в один: для ШІ-шляху це картка R15. Пари конфліктів лишити й показати їх у симуляції як відхилені спроби, не лише як помилку після Apply.
- **Прийняття.** Зміна ваги одразу змінює показаний %. Сухий прогін не викликає рушій. «Рівно N» або виконується, або build падає з іменами рис.
- **Тести.** Розширити `test/wave3.test.mjs` і тести рецептів: частка ваг; прапорець bypass не ламає унікальність решти; лічильник N.
- **Обсяг / пріоритет.** M / **P1**.
- **Залежності.** Не блокує P0. Симуляція рідкості корисна звіту R9.
- **Документація.** [HashLips image layers](https://lab.hashlips.io/docs/art-engine/core-plugins/inputs/image-layers), [issue про bypassDNA](https://github.com/HashLips/hashlips_art_engine/issues/251), [OpenRarity](https://openrarity.gitbook.io/developers/fundamentals/methodology). Оцінка «drip» Milady (рідкість = читаність у мініатюрі) — якісна ідея з [блогу](https://blog.remilia.org/milady-maker/); числової шкали звідти не витягували, в продукт її не копіювати як метрику.

### Генерація: консистентність

#### R7. Триматися бази, не ланцюга правок

**Статус: зроблено.**

- **Проблема.** Дослідження (стаття Kontext) описує дрейф ідентичності на довгому ланцюгу edit. Lab уже шле базову картинку в кожен кадр кроку Генерації — це треба зберегти й не замінити «попереднім кадром як новою базою».
- **Зараз у коді.** Пакетна генерація бере базову картинку серії або лінійну базу, не попередній кадр набору. Підказка на Генерації каже: кожен кадр іде від базової картинки серії (або від лінійної бази), не від сусіднього кадру. Окремої кнопки «редагувати від попереднього видання» немає. Шлях Б може зібрати нову головну базу з тексту — це інший режим, і без головної бази edit не стартує.
- **Зміна.** Не додавати ланцюг «кадр N як референс кадру N+1» у типовий шлях. У довідці кроку Генерації одне речення: кожен кадр іде від базової картинки серії (або від лінійної бази), не від сусіда. Якщо колись з’явиться «допрацювати цей кадр» — окрема дія з попередженням про дрейф, не новий дефолт.
- **Прийняття.** Типовий batch як і раніше читає файл з `input/`, не з `out/<set>/`.
- **Тести.** Існуючий шлях генерації: мок отримує байти primary, не попередній png набору.
- **Обсяг / пріоритет.** S / **P1** (переважно захист і текст; коду майже немає).
- **Залежності.** R4.
- **Документація.** [arXiv:2506.15742](https://arxiv.org/abs/2506.15742), [блог Kontext](https://bfl.ai/blog/flux-1-kontext). Поріг «шість правок» — резюме статті, не наш вимір.

#### R8. Об’єктивна схожість поруч із критиком

**Статус: зроблено.** Метрика — середній хеш, не ембедінг обличчя.

- **Проблема.** LLM-критик оцінює якість і «чи видно риси», але не має числового порога ідентичності й не блокує архів. gremlin-nft відхиляє чергу нижче 6 і не пускає в бандл кадр нижче 7. У Lab такий гейт свідомо відкладений ([ROADMAP.md](./ROADMAP.md): критик не обов’язковий). Дослідження: IP-Adapter тримає стиль краще за особу; для особи потрібне порівняння ембедінгів або донавчання.
- **Зараз у коді.** Критик лишається дорадчим: шкала 1–10, вердикти keep / review / redo. У Відборі є «Схожість до бази»: гістограми напрямів країв (`hog-aligned-1` у `src/similarity.mjs`): обрізка підлаштовується під зсув і масштаб камери, колір ігнорується. Нижче `SIMILARITY_WARN_BELOW` (0.73) це попередження, не заборона ZIP. Раніше стояв середній хеш 64 біти (`ahash-64`): на живому тесті 08.10.2026 запас між своїми й чужими кадрами був 0,016, нині 0,084. Ембедінга обличчя і CLIP немає: дзеркальна копія бази оцінюється як сама база, а метрика припускає центроване кадрування по груди. Пороги «відмова нижче 6» і «ZIP не бере keep нижче 7» не додавались.
- **Зміна.** Не вмикати жорсткий гейт «нижче 7 не пакувати» без окремого продуктового рішення: це суперечить поточному ROADMAP. Натомість поруч із вердиктом критика показувати **опційну** числову схожість до базової картинки (ембедінг; модель обрати в тому PR, з ліцензією ваг). Поріг — попередження у відборі, не помилка preflight, доки власник не скаже інакше.
- **Прийняття.** Архів без цієї метрики збирається як зараз. Якщо метрика увімкнена, картка кадру показує число, а низьке значення не пише HTTP 422 саме по собі.
- **Тести.** Фікстура двох png: метрика детермінована й не ходить у мережу в офлайн-режимі.
- **Обсяг / пріоритет.** L / **P1**.
- **Залежності.** R4 (інакше «далекий» кадр може бути наслідком мертвого повзунка, а не моделі).
- **Документація.** [IP-Adapter](https://arxiv.org/abs/2308.06721). Жорсткий поріг gremlin не копіювати мовчки — він розходиться з [ROADMAP.md](./ROADMAP.md).

### Галерея і відбір

#### R9. Читаність квадратної мініатюри

**Статус: зроблено.**

- **Проблема.** Колекції PFP дивляться в квадраті й у дрібному розмірі. Кадр, який гарний на 1024 і втрачає обличчя в кропі, не має бути несподіванкою на маркеті.
- **Зараз у коді.** У Відборі є перемикач «Мініатюра 64px поруч». Великий кадр лишається. Окремого автоматичного напису «обличчя випало з кропу» немає.
- **Зміна.** У відборі перемикач дрібного квадрата (порядок 64px) поруч із поточним тайлом. Це перегляд, не другий файл. Не різати вихідний png автоматично.
- **Прийняття.** Той самий файл виглядає великим і дрібним; архів не змінюється від перемикача.
- **Тести.** Немає окремого юніта на CSS. Достатньо ручної перевірки двох кадрів: квадрат і широкий.
- **Обсяг / пріоритет.** S / **P1**.
- **Залежності.** Немає.
- **Документація.** Якісний прийом з [Milady](https://blog.remilia.org/milady-maker/) (кроп під квадратний PFP). Пікселі слотів маркетів — уже в `src/marketplace-kit.mjs`, їх не дублювати тут.

#### R10. Попередження про розмір файлу близько 1 МБ

**Статус: зроблено.** Попередження є; кнопка «Стиснути до 1 МБ» є (11.10.2026 звірено з кодом).

- **Проблема.** Підготовка асетів Core Candy Machine просить тримати файли до 1 МБ, де це можливо. Зараз ворота архіву пропускають значно більші png.
- **Зараз у коді.** `PREFLIGHT_RECOMMENDED_IMAGE_BYTES` дорівнює 1 МіБ. Файл більший дає попередження і не блокує ZIP. Стеля `PREFLIGHT_MAX_IMAGE_BYTES` (типово 20 МБ) лишається помилкою. Стиснення кадрів за кнопкою («Стиснути до 1 МБ» на вкладці Експорт, `POST /api/set/compress`, `src/compress.mjs`): спершу менше кольорів, якщо мало, трохи менший розмір; оригінал лишається у версіях кадру (`versions/`), тиха заміна оплаченого файлу не відбувається. `src/png-fit.mjs` змінює розмір лише банера, аватара й обкладинки набору маркету.
- **Зміна.** Попередження preflight (не помилка), якщо png більший за 1 МБ: посилання на пораду Metaplex і на те, що ZIP усе одно збереться. Окреме стиснення — лише за кнопкою, з новою версією кадру (`addVersion`), не тихою заміною оплаченого файлу. Поріг винести в константу з коментарем-цитатою, не магічне число в UI.
- **Прийняття.** Файл 2 МБ дає warning і HTTP не 422 лише через розмір, доки він менший за `PREFLIGHT_MAX_IMAGE_BYTES`. Файл понад стелю як і раніше помилка.
- **Тести.** Розширити `test/preflight.test.mjs` двома розмірами.
- **Обсяг / пріоритет.** S / **P1**.
- **Залежності.** Немає. Стиснення за кнопкою — M, можна другим комітом тієї ж фази.
- **Документація.** [Preparing assets](https://www.metaplex.com/docs/smart-contracts/core-candy-machine/preparing-assets): «keep file sizes under 1 MB where possible».

### Експорт і перевірка архіву

#### R11. Унікальність комбінацій і майже-дублікати

**Статус: зроблено.**

- **Проблема.** Два кадри з тим самим DNA або тією самою картинкою не повинні потрапити в ZIP. Майже однакові картинки з різним хешем файлу зараз не блокують випуск — і це свідоме рішення PRODUCT (перцептивний дубль лишається інструментом відбору).
- **Зараз у коді.** Однаковий DNA і однаковий SHA-256 картинки — помилки перевірки архіву, ZIP не пишеться. Середній хеш (aHash) лишається попередженням у Відборі, не блоком архіву. Шар із `skipDna: true` не входить в унікальність; без цього прапорця ключ входить.
- **Зміна.** Прапорець шару з R6 має збігатися з DNA у preflight (один хелпер). aHash лишити попередженням у звіті preflight, не новою помилкою 422: інакше розйдемося з пунктом 4 розділу «свідомо не в цій зміні» у [PRODUCT.md](./PRODUCT.md). Жорсткий стоп — лише якщо власник окремо змінить PRODUCT.
- **Прийняття.** Два однакові DNA з вимкненим bypass — помилка, як зараз. Два близькі png — warning із номерами видань. ZIP при одному лише warning пишеться.
- **Тести.** Існуючі тести preflight плюс фікстура двох png з малим Hamming distance для warning.
- **Обсяг / пріоритет.** M / **P1**.
- **Залежності.** R6 для прапорця шару. Warning по aHash можна зробити раніше.
- **Документація.** [HashLips bypass](https://github.com/HashLips/hashlips_art_engine/issues/251).

#### R12. Звіт рідкості: OpenRarity, статистичний, null

**Статус: частково.** Другий звіт OpenRarity є. HowRare і MoonRank не зроблені.

- **Проблема.** Зараз бал видання — сума `1 / частота` по наявних рисах. Відсутня риса викидається, а не стає значенням. Це ближче до спрощеного HowRare без балів за кількість рис і **не** OpenRarity. Формулу HowRare (сума 1/rarity% плюс бали за число рис) сторінка FAQ з цього середовища не віддала — реалізовувати її як «офіційну HowRare» не можна, доки FAQ не прочитаний.
- **Зараз у коді.** Частотний звіт лишився. Поруч `openRarityByEdition` у `src/rarity.mjs`: сума −log2(P), відсутнє значення шару пишеться як «null». Той самий бал їде в архів і в картку рідкості. HowRare не вмикався: сторінка FAQ відповіла HTTP 403, формулу не перечитували. MoonRank (добуток відсотків) лишається UNVERIFIED і в коді його немає.
- **Зміна.** Другий звіт поруч, не замість поточного: OpenRarity = сума −log2(P), відсутнє значення шару входить як окреме «null», якщо шар у пресеті існує. Підпис методу в `rarity.txt`. Статистичний варіант (z-score частот) — лише якщо беремо формулу з відкритої сторінки; інакше не вигадувати. HowRare-сумісний режим не вмикати, доки FAQ `https://howrare.is/faq` (HTTP 403, не відкривалось) не прочитаний людиною. MoonRank (добуток відсотків) — **UNVERIFIED**, не реалізовувати.
- **Прийняття.** Один і той самий архів дає старий бал і окремий бал OpenRarity. Видання без риси в одному шарі не збігається з виданням, де ця риса є.
- **Тести.** Маленький архів із навмисним null: очікуваний −log2 вручну в тесті.
- **Обсяг / пріоритет.** M / **P1**.
- **Залежності.** Немає.
- **Документація.** [OpenRarity methodology](https://openrarity.gitbook.io/developers/fundamentals/methodology). HowRare і MoonRank — див. розділ неперевіреного.

#### R13. Критик проти заявлених рис

**Статус: зроблено.**

- **Проблема.** img2img не гарантує, що в метаданих написано те, що на картинці. Зараз критик просить «перевірити ключові риси» одним загальним тегом `missing_trait`.
- **Зараз у коді.** Критик повертає `missingTraits`: ключі рис рецепта, яких на кадрі не видно. Непорожній список додає тег `missing_trait`. ZIP через це не блокується. Евристичний triage як і раніше дивиться файл і промпт, не пікселі окремої риси.
- **Зміна.** Просити в моделі список рис, яких не видно, ключ у ключ із рецептом. Звіт архіву: скільки кадрів мають `missing_trait` після людського або AI triage. Не блокувати ZIP автоматично (той самий принцип, що R8).
- **Прийняття.** Відповідь критика містить масив відсутніх ключів або порожній масив. Евристика без Vision не вигадує, що риса «видно».
- **Тести.** `sanitizeCriticOutput` приймає і чистить новий масив. Офлайн-режим не ставить `missing_trait` лише через текст промпта.
- **Обсяг / пріоритет.** M / **P1**.
- **Залежності.** Немає. Корисний разом із R8.
- **Документація.** Внутрішній контракт критика. Межа моделі — [IP-Adapter](https://arxiv.org/abs/2308.06721): збіг стилю не є збігом предмета.

### Провененс і розкриття

#### R14. Хеш провененсу вже є — додати зерно порядку й хеш hidden settings

**Статус: зроблено.**

- **Проблема.** Провененс BAYC фіксує порядок зображень. Core Candy Machine для розкриття фіксує SHA-256 масиву `{name, uri}`. thirdweb фіксує keccak256 від base URI, пароля і chain id всередині зашифрованого батчу. Зараз Lab рахує ланцюг SHA-256 картинок і не кладе в файл ні зерно перемішування, ні заготовку hidden settings, ні поля delayed reveal.
- **Зараз у коді.** `calculateCollectionProvenance` як і раніше сортує за виданням і хешує зчеплені SHA-256. У запис додається `presetSeed`, коли зерно пресету задане. Набір деплою типово кладе `cm-config.json` і чернетку `hidden-settings.json` без пароля. Sugar пишеться лише для пункту «Solana (Sugar, застарілий)», у теку `sugar/`.
- **Зміна.** У `provenance.json` додати `presetSeed` (вже відомий людині seed пресету — не новий секрет) і назву алгоритму, яка вже є. Для Solana-набору деплою — файл-заготовка `hidden-settings.json`: placeholder name/uri і інструкція порахувати SHA-256 так, як у гайді Core (хеш масиву reveal data, не вигадувати власний формат). Для EVM — поля в `thirdweb.json`: що людина введе пароль **у себе** в кабінеті thirdweb; Lab пароль не приймає і не зберігає (інакше це секрет, який `rejectSecrets` уже відсікає).
- **Прийняття.** Старий хеш картинок не змінює формулу. Нові поля опційні для вже зібраних архівів. Будь-яке поле з виглядом пароля або ключа в тілі набору як і раніше 400 `secrets`.
- **Тести.** Існуючі тести провененсу плюс відмова набору, якщо в hidden-settings покласти password / secret.
- **Обсяг / пріоритет.** M / **P1**.
- **Залежності.** Краще після R16, щоб заготовка лягла в Core-набір, а не в Sugar-набір як у єдиний шлях. Файл провененсу можна раніше.
- **Документація.** [розбір BAYC](https://dev.to/brodan/learning-nft-provenance-by-example-a-bored-ape-investigation-hfe), [hidden settings](https://www.metaplex.com/docs/smart-contracts/core-candy-machine/guides/create-a-core-candy-machine-with-hidden-settings), [thirdweb delayed reveal](https://portal.thirdweb.com/tokens/build/base-contracts/erc-721/delayed-reveal).

## Відома вразливість залежності (05.10.2026)

`npm audit --omit=dev` показує high для `bigint-buffer@1.1.5` (переповнення буфера в `toBigIntLE()`, GHSA-3gc7-fjrx-p6mg), виправлення немає. Шлях: `@solana/spl-token` → `@solana/buffer-layout-utils` → `bigint-buffer` (`@irys/upload-solana` теж тягне його). Код репозиторію `toBigIntLE` не викликає (`grep` по `src`, `server`, `bin`, `scripts` порожній), вхідні дані користувачів до цієї функції не доходять: Solana-операції йдуть у CLI на ПК. Ризик для сервера прийнято. Раз на місяць запускати `npm audit` і оновлювати `@irys/*` та `@solana/spl-token`, щойно вийде версія без `bigint-buffer`.
